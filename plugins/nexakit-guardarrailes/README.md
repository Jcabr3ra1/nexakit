# nexakit-guardarrailes

El mod comprueba las llamadas a `Bash`, `Write`, `Edit` y `MultiEdit` antes de que Claude Code las ejecute.
Cuando una regla se activa, explica el motivo y cómo continuar de forma deliberada. El análisis es local y
no guarda datos entre llamadas. Si falla, la llamada sigue su curso.

Instálalo desde Claude Code con `/plugin marketplace add Jcabr3ra1/nexakit` y
`/plugin install nexakit-guardarrailes@agent-toolkit`. También puedes seleccionarlo en el asistente de `npx nexakit`.

## Comandos peligrosos

- `rm -rf` sobre `/`, `~`, `$HOME`, `.`, `..` o `*`.
- `git push --force` y `git push -f`.
- `git reset --hard`, `git clean -fd`, `git checkout .` y `git restore .`.
- `git branch -D` sobre `main` o `master`.
- `chmod -R 777` y las descargas de `curl` conectadas a `sh` o `bash` mediante una tubería.

`git push --force-with-lease` y `echo "rm -rf /"` pasan. Para permitir una operación a propósito,
pon `NEXAKIT_PELIGRO=1` delante del comando, por ejemplo `NEXAKIT_PELIGRO=1 git reset --hard`.
En una tubería de descarga, pon el prefijo delante de `curl`.

## Archivos sensibles y secretos

En `Write`, `Edit` y `MultiEdit` revisa el destino y el texto que se añade. En Bash revisa el destino de
`>` y `>>` y el contenido literal de `echo`, `printf`, los heredocs y las cadenas de entrada que alimentan la
escritura. Bloquea los nombres `.env`, `.env.*`, `*.pem`, `*.key`, `id_rsa*` y `credentials*`.
Puedes escribir en `.env.example` con valores de ejemplo.

Bloquea contenido con patrones de claves `sk-`, `AKIA`, `ghp_`, `xoxb-`, `xoxp-` y encabezados de
clave privada. El mensaje de bloqueo omite el valor detectado.

Para permitir una escritura deliberada en Bash, pon `NEXAKIT_SECRETO=1` delante del comando que redirige, por ejemplo
`NEXAKIT_SECRETO=1 printf '%s\n' 'MODO=local' > .env`. Para continuar con una escritura bloqueada desde
`Write`, `Edit` o `MultiEdit`, confirma la operación con la persona.

## Mensajes de commit

Para `git commit`, revisa el mensaje cuando puede extraerlo de `-m`, de varios `-m` o de un heredoc.
La primera línea debe seguir `tipo(alcance opcional): descripción`, tener hasta 72 caracteres y llevar
una descripción en minúsculas y sin punto final. Los tipos admitidos son `feat`, `fix`, `docs`, `style`,
`refactor`, `test`, `chore`, `perf`, `ci` y `revert`. El mensaje completo debe quedar libre de tráileres
`Co-Authored-By` y de firmas de autoría de herramientas externas («Generado con Claude», «Generated by
Codex», el emoji 🤖). Nombrar una herramienta en el mensaje, como «corregir la skill de codex», sí se permite.

`git commit -m "fix(cli): valida los comandos"` pasa. También pasan `git commit` y `git commit --amend`
cuando no se proporciona un mensaje comprobable. Usa `NEXAKIT_COMMIT=1` delante de `git commit` para
permitir deliberadamente un mensaje fuera del formato.

```bash
git commit -F - <<'MENSAJE'
feat(cli): añade las reglas

Comprueba las llamadas antes de ejecutarlas.
MENSAJE
```

El análisis de Bash se limita a comandos simples y datos visibles en la llamada. Las expansiones, los alias y los
scripts que se invocan se resuelven al ejecutar Bash. Si el mensaje depende del editor, de una expansión dinámica
o de un archivo externo, el commit sigue su curso.
